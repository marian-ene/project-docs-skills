# C# implementation practices

Apply these defaults when implementing or reviewing C# code in scope. Follow agreed team standards. Confirm a consequential conflict or departure before introducing a new pattern. Existing code shows how the system behaves; it does not make every existing pattern a standard. Do not migrate unrelated code, change public contracts, or upgrade the language or runtime just to adopt this guide.

## Readability and C# style

- Choose the simplest implementation that preserves correctness, performance, and architectural boundaries. Use explicit control flow and domain-specific names, including in lambdas. Spell out `cancellationToken`; avoid abbreviations such as `ct` and `ctx`.
- Use file-scoped namespaces where supported, with `using` directives outside the namespace. Inject dependencies through explicit constructors into `private readonly` fields rather than using primary constructors. Use braces even for single-statement control flow.
- Prefer `var` for locals unless an explicit type is necessary for correctness or clarity. Prefer collection expressions such as `[]` where the language version and target type support them. Prefer `IReadOnlyList<T>` or `IReadOnlyDictionary<TKey, TValue>` when callers only read; keep mutable collections internally as needed.
- Separate logical phases, substantial queries, awaited results, and mapping blocks with one blank line. Leave one blank line after a completed `if`, `switch`, `for`, or `foreach` when another statement follows; keep `else` with its `if`. Comment non-obvious intent, not the code's mechanics. Do not add routine XML docs or leave TODO comments.
- Keep production validation and error messages in the owning module's `Constants/ErrorMessages.cs` and other application strings or format templates in `Constants/Strings.cs` or a clearly named equivalent. Reuse existing constants, preserve localization and contract values, and use `nameof` for CLR member names and `string.Empty` for an empty string.

## Backend boundaries and vertical slices

- Keep controllers and function endpoints thin: bind transport input, obtain necessary authenticated caller context, delegate, and map the outcome. Preserve meaningful binding distinctions such as absent versus supplied-empty. Keep semantic parsing, validation, and business logic in application code; do not pass HTTP request or context objects into it.
- In a backend organized around application modules, reuse the owning bounded context. Give each use case a verb-first `Features/{Feature}/` slice. Expose one behavioral entry point per module, `I{Context}Application`, with an internal facade that delegates without adding business logic. Keep public request and response records in `Contracts/{Feature}/`, not in service files, and do not expose persistence entities as contracts. Register dependencies in the owning module through host composition, with lifetimes that match state and resource ownership.
- Keep feature services, validators, mappers, actions, and implementation models internal and seal classes when inheritance is not intended. Put interfaces in their own files beside implementations. Do not reference another slice's implementation, even via its internal interfaces. Share legitimate domain or infrastructure building blocks and public contracts; prefer a small feature-local duplicate over cross-slice coupling. Extend an established worker pipeline in place instead of adding a parallel processing path or forcing an API facade onto it.
- Keep `Handle` or `HandleAsync` readable as the use case: validate, call focused actions, propagate errors, and map the response. Use inline guards for simple inputs and pure validators for multi-field requests. Extract substantial parsing, branching, and mapping into focused methods or feature-local helpers without I/O. Do not hide the action sequence in a second coordinator or pass the workflow as a callback to a resource-lifetime helper.
- In slices that use actions, give each query, command, or HTTP operation its own interface, class, files, and folder under `Actions/`. A database action performs one explicit database operation per invocation; a composed query can still contain joins and grouping. Do not chain actions inside an action or hide additional I/O in helpers. Resolve shared prerequisites once where safe, and do not increase round trips or split a required transaction just to separate actions.

## EF Core and persistence

- For independent EF Core reads, create and dispose a context through the configured factory. Never run concurrent operations on one context. Share a context and transaction when the use case needs atomic writes or a consistent multi-read snapshot; resource helpers own lifetime, not business orchestration.
- Use no-tracking reads and narrow projections where appropriate. Verify schema, foreign keys, and nullability; prefer direct FK predicates for simple lookups and avoid loading whole entities or JSON just to obtain a field. Reuse a verified view for genuinely complex relational reads: check its definition, mapping, cardinality, and active-row behavior, including joined rows. Keep simple queries simple, and inspect actual SQL and execution plans before claiming a performance gain.
- Preserve active-row filtering, soft deletion, audit, and concurrency semantics. Use targeted updates when compatible with the unit of work, interceptors, audit, and concurrency requirements; otherwise use the appropriate tracked or bulk write path. When a targeted update must match a row, use its affected-row count instead of a separate existence lookup. Do not use the count from `SaveChangesAsync` as a general not-found test.

## Errors, cancellation, and contracts

- Use the established typed result/error pattern for expected failures rather than throwing business exceptions. A missing requested resource is an explicit error unless the contract says otherwise; zero matches is a successful empty collection. Do not turn failed dependencies into successful nulls, empty results, or silent returns. Use the existing diagnostic path without exposing sensitive details. For workers, preserve exceptions when the host needs them for retry or message settlement.
- Pass the caller's `CancellationToken` through the entire affected path, including async validation, EF operations, HTTP send and response reading. Let caller-requested cancellation propagate through exception handlers instead of converting it into an error response. Distinguish cancellation from dependency timeouts.
- Use configured HTTP clients and typed downstream contracts. Unwrap downstream envelopes at the integration boundary and generate the outgoing envelope only once if required. Keep file or stream paths separate where the contract requires it. Preserve downstream failure semantics and do not add retries that could repeat mutations without verifying idempotency.
- Verify the actual wire contract: property names and casing, explicit `null` versus omission, `[]` for empty lists where specified, and the envelope shape. Do not change global serialization settings for one endpoint.

## Verification

- Use the existing test stack. Write focused, deterministic tests with one behavior per case and clear Arrange/Act/Assert phases. Prefer strict mocks when supported; test that invalid input does not invoke downstream actions. Cover relevant success, invalid input, not-found, dependency failure, and cancellation behavior.
- Verify changed endpoints and wire contracts at the HTTP boundary. Use the relevant database provider to verify SQL, constraints, or transaction behavior when those change; mocks and in-memory providers do not prove them. Test retry or settlement behavior at the worker boundary when it changes.
